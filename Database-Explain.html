Database Design — Stengg Fashion Ecom

Overview

The basic database for Fasion Shop is structured around four core tables. All main entities inherit from a shared FullAuditedEntity base class, which provides a consistent auditing mechanism across the system.

Base Class — FullAuditedEntity

Before describing individual tables, it is important to understand the base class that most entities inherit from.

Field Type Description
CreationTime DateTime Timestamp when the record was created. Defaults to DateTime.UtcNow.
LastModificationTime DateTime? Timestamp of the most recent update. Null if never modified.
DeletionTime DateTime? Timestamp when the record was soft-deleted. Null if active.
IsDeleted bool Soft-delete flag. Records are never physically removed; they are marked as deleted instead.
CreatorUserId int? ID of the user who created the record.
LastModifierUserId int? ID of the user who last modified the record.
DeleterUserId int? ID of the user who deleted the record.

Soft Delete: Instead of permanently removing records from the database, the system sets IsDeleted = true and records the DeletionTime. This preserves historical data and supports data recovery.

Table 1 — Categories

Purpose: Stores the product categories used to organize and classify products in the shop (e.g., T-Shirts, Jackets, Accessories).

Inherits: FullAuditedEntity

Column Type Constraints Description
Id int Primary Key Auto-incremented unique identifier.
Name string Required, max 512 chars Display name of the category.
Description string Required A text description of the category.

Relationships:

  • One Category → many Products (one-to-many)

Table 2 — Products

Purpose: Stores the core information of each product in the catalog. A product represents a general item (e.g., Slim Fit Chino Pants) before any specific size or color is defined.

Inherits: FullAuditedEntity

Column Type Constraints Description
Id int Primary Key Auto-incremented unique identifier.
CategoryId int Foreign Key → Categories The category this product belongs to.
Name string Required, max 512 chars Display name of the product.
Description string? Nullable Optional product description.
RowVersion byte[] Timestamp / Concurrency Token Used for optimistic concurrency control — prevents two users from overwriting each other's changes simultaneously.

Relationships:

  • Many Products → one Category (many-to-one)
  • One Product → many ProductVariants (one-to-many)

Table 3 — ProductVariants

Purpose: Represents a specific, purchasable version of a product — defined by a unique combination of size, color, and price. For example, the product Slim Fit Chino Pants may have variants such as (M, Black, $29.99) and (L, Beige, $29.99).

Inherits: FullAuditedEntity

Column Type Constraints Description
Id int Primary Key Auto-incremented unique identifier.
ProductId int Foreign Key → Products The parent product this variant belongs to.
Size string Max 32 chars The size of this variant (e.g., S, M, L, XL).
Color string Max 32 chars The color of this variant (e.g., Black, White).
Price decimal(18,2) — The selling price of this variant.
IsSell bool Default: false Indicates whether this variant is currently listed for sale.
RowVersion byte[] Timestamp / Concurrency Token Optimistic concurrency control, same as Product.

Relationships:

  • Many ProductVariants → one Product (many-to-one)
  • One ProductVariant → one ProductInventory (one-to-one)

Table 4 — ProductInventories

Purpose: Tracks the stock levels for each ProductVariant. It is intentionally separated from ProductVariants to keep inventory concerns (stock management) decoupled from product description concerns (size, color, price). This separation makes it easier to scale up and multi-warehouse by the way change 1-n relationship between ProductVariants - ProductInventories. To make it more simplier you can remove this table and put quantity fields into ProductVariant.

Column Type Constraints Description
Id int Primary Key Auto-incremented unique identifier.
ProductVariantId int Foreign Key → ProductVariants The variant this inventory record belongs to.
StockQuantity int — The total quantity ever received into stock for this variant.
RemainingQuantity int — The current quantity still available for purchase.
IsDeleted bool Default: false Soft-delete flag (note: does not inherit FullAuditedEntity).

StockQuantity vs RemainingQuantity: StockQuantity records how much was originally stocked, while RemainingQuantity decreases as orders are placed. The difference between the two reflects how many units have been sold or reserved.

Relationships:

  • One ProductInventory → one ProductVariant (one-to-one)
